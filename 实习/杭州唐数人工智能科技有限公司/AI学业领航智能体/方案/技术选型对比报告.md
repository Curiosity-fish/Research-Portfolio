# 学业领航智能体平台 — 技术选型对比报告

**文档版本：** v1.0  
**日期：** 2026-06-22  
**适用范围：** 招标文件三大项目全栈技术选型

---

## 一、选型原则

| 原则 | 说明 |
|------|------|
| 可落地优先 | 优先选择在中国高校/教育行业已有成熟部署案例的技术 |
| 国产优先 | 数据安全敏感场景优先国产开源，降低等保三级合规风险 |
| 运维成本低 | 团队规模有限，不选维护复杂度超出交付能力的技术 |
| 招标合规 | 所有AI模型须经国家网信办备案，不得使用未备案境外模型直接接入学生数据 |
| 统一技术栈 | 三大项目尽量共用后端语言/框架，降低跨团队沟通成本 |

## 二、数据工程与治理服务技术选型

### 2.1 数据仓库 / OLAP 引擎

**需求背景：** 需支持 ODS→DWD→DWS→ADS 四层架构，兼顾批量全量调度（日级）与准实时增量同步，历史数据保留 ≥5 年，12 张以上应用宽表查询性能达标。

| 候选方案 | 优势 | 劣势 | 国内教育案例 |
|---------|------|------|------------|
| **Apache Doris** | 国产开源；支持实时+批量混合；SQL 兼容 MySQL 语法；向量化执行引擎，小数据量查询 P95 <100ms；Join 能力强，适合多表宽表 | 集群运维相对复杂；Standalone 单节点支持有限 | 多所 985/211 用于教务分析，阿里云上线 SelectDB 版本 |
| **ClickHouse** | 单节点写入/查询性能极强；列存压缩率高 | Join 能力弱（建议宽表预先 Join）；中文社区支持不如 Doris；多表 Join 复杂场景需开发成本 | 互联网公司为主，高校场景少 |
| **StarRocks** | 性能略优于 Doris（同根同源）；Shared-Nothing 架构 | 商业版功能受限；社区版文档不如 Doris 完善；国内 AI 场景接入案例少 | 主要在互联网/金融 |
| **Hive + Spark** | 生态成熟；与 Hadoop 集成完美 | 延迟高（分钟级），不满足准实时要求；运维复杂度高；需要 YARN/HDFS 基础设施 | 传统高校大数据平台，但技术路线老旧 |

**✅ 推荐选型：Apache Doris**

- 原生支持四层数仓架构，DWS 层 Rollup 物化视图加速聚合查询
- SQL on MySQL 方言，Spring Boot 直接用 JDBC 接入，无需额外驱动
- 单节点（1 FE + 1 BE）足以支撑高校规模数据量（百万级学生记录），日后横向扩展
- 内置数据导入接口（Stream Load / Routine Load）覆盖批量/准实时两种场景

---

### 2.2 ETL 调度平台

**需求背景：** 需支持 DAG 依赖管理、任务失败告警、每日全量 6:00 前完成、日志保留 90 天，具备数据血缘追踪。

| 候选方案 | 优势 | 劣势 |
|---------|------|------|
| **Apache DolphinScheduler** | 国产开源；Web UI 完善，工作流可视化拖拽；DAG/依赖管理完整；中文文档丰富；支持 Master-Worker 高可用；已通过多所高校验证 | 相比 Airflow，插件生态稍弱 |
| **Apache Airflow** | 生态最丰富；Python 脚本灵活；全球用户量最大 | 界面中文化差；运维复杂；团队需 Python 开发能力；国内高校少用 |
| **XXL-Job** | Java 生态；轻量级；与 Spring Boot 完美整合 | 缺乏 DAG 依赖管理；不适合复杂多阶段 ETL 编排 |
| **Quartz** | 嵌入式，无需独立部署 | 无 UI，不支持 DAG，不满足需求 |

**✅ 推荐选型：Apache DolphinScheduler 3.x**

- DAG 依赖管理原生支持，上下游任务阻塞/并行控制开箱即用
- 内置任务失败告警（邮件/企微/钉钉），满足 1.4.2 要求
- 日志保留策略可配置（90天），并支持任务/时间维度查询
- 数据血缘：DolphinScheduler 3.x 引入 Lineage 模块，可可视化追踪字段级血缘

---

### 2.3 数据采集 / 接入工具

**需求背景：** 需支持 API 对接、数据库直连、文件批量导入，增量+全量两种模式，接口重试机制，准实时同步。

| 候选方案 | 适用场景 | 说明 |
|---------|---------|------|
| **DataX（阿里开源）** | 批量全量 / 增量文件同步 | 支持 20+ 种数据源（MySQL, Oracle, PostgreSQL, HDFS, HTTP），Reader/Writer 插件化；高校业务系统接口形式多样，DataX 覆盖面最广 |
| **Canal（阿里开源）** | MySQL 准实时增量（CDC） | 监听 MySQL Binlog，实现秒级增量同步；教务系统/一卡通系统基于 MySQL 时首选 |
| **Flink CDC** | 多源准实时 CDC | 支持 MySQL/PostgreSQL/Oracle CDC；功能更强但运维复杂度高，对于当前规模偏重 |
| **HTTP 自研采集器** | 业务系统 REST API 对接 | 部分系统仅提供 API，需定制采集服务（Java/Python 均可） |

**✅ 推荐组合：DataX（批量）+ Canal（准实时增量）+ 自研 HTTP 采集器（API 对接）**

- 三者互补，覆盖文档所有接入场景
- DataX 和 Canal 均由 DolphinScheduler 统一调度管理
- 自研 HTTP 采集器控制层写在 Spring Boot 内，复用后端基础设施

---

### 2.4 数据质量监控

**需求背景：** 覆盖完整性/一致性/准确性/时效性，自动生成日报，超阈值告警，工单机制，≥98% 完整率监控。

| 候选方案 | 优势 | 劣势 |
|---------|------|------|
| **Apache Griffin** | 专为大数据数据质量设计；支持 Doris/Hive 接入；规则配置化 | 界面老旧，社区不活跃（最后版本 2019年）；与新版 Doris 集成需适配 |
| **Great Expectations** | Python 生态，规则丰富，文档好 | 主要面向 Python 用户；界面为英文；高校场景少 |
| **Soda Core** | 轻量级；支持 SQL 数据源 | 商业版收费，开源版功能受限 |
| **自研质量检测模块** | 完全契合需求；与 DolphinScheduler 无缝集成；可内嵌工单系统 | 开发成本约 3-4 人周 |

**✅ 推荐选型：自研数据质量检测模块（内嵌于 DolphinScheduler）**

- 基于 SQL 断言检测（Doris 原生 SQL），开发成本可控
- 规则以配置文件形式存储（YAML/JSON），满足无需发版即可调整阈值的要求
- 工单系统可直接复用平台内的消息通知模块
- Apache Griffin 社区已实质停维，不建议引入

---

### 2.5 加密与数据安全

**需求背景：** AES-256 字段级加密，等保三级，RBAC，操作日志 180 天。

| 层级 | 选型 | 说明 |
|------|------|------|
| 字段加密 | **Jasypt + AES-256-GCM** | Spring Boot 生态原生支持；Jasypt 用于配置文件密钥保护，应用层加密/解密透明 |
| 访问控制 | **Spring Security + RBAC 模型** | 与 Spring Boot 天然集成；基于角色注解控制数据查询范围 |
| 操作审计日志 | **自研 AOP 切面 + MySQL 审计表** | 拦截所有数据访问请求，记录操作人/时间/对象，保留 180 天 |
| 等保三级 | 部署阶段配合学校网络安全团队完成测评 | 代码层满足 OWASP Top10；网络层由学校IT配合 |

## 三、学业领航系统平台开发技术选型

### 3.1 前端框架

**需求背景：** 响应式，1280×720+，组件化，ECharts 图表，PDF 导出。

| 候选方案 | 优势 | 劣势 |
|---------|------|------|
| **Vue 3 + TypeScript** | 与现有 Demo 一致；Element Plus 生态；国内高校系统主流；学习曲线低 | 相比 React，大型应用状态管理稍复杂 |
| **React 18 + TypeScript** | 社区最大；Hooks 成熟；RSC 支持好 | 国内教育项目切换成本高；Ant Design 风格与现有设计系统不完全一致 |

**✅ 推荐选型：Vue 3.4 + TypeScript + Vite 5**

- 现有 Demo 已基于此栈，存量代码可直接复用
- Element Plus 2.14+（全量图标注册，国际化支持）
- Pinia 作为状态管理（比 Vuex 更轻量）
- ECharts 5.x 用于所有图表（热力图/折线图/雷达图/饼图），全部已经过验证

**图表：ECharts 5.x**（文档明确要求，直接锁定，无需比较）

---

### 3.2 后端框架

**需求背景：** RESTful API，接口版本管理，Swagger 文档，500-1000 并发，等保三级环境。

| 候选方案 | 优势 | 劣势 |
|---------|------|------|
| **Spring Boot 3.x (Java 17)** | 国内高校行政系统标配；Java 人才储备充足；与 MySQL/Redis 集成最成熟；Spring Security 等保三级支持完善；Swagger 3.0 原生支持 | 启动慢；代码量较多 |
| **FastAPI (Python 3.12)** | 性能优秀；AI 服务调用天然方便（与 LangChain/LlamaIndex 同生态）；异步原生 | 国内高校 Java 开发者多，Python 后端运维经验少；等保三级合规案例少 |
| **NestJS (Node/TypeScript)** | TypeScript 全栈统一；与前端同语言 | 高校 IT 团队 Node.js 后端经验稀缺；生产稳定性案例少 |
| **Django (Python)** | 自带 Admin 后台；ORM 成熟 | 性能不如 Spring Boot；异步支持不如 FastAPI |

**✅ 推荐选型：Spring Boot 3.3 (Java 17) + Spring Security**

- 后端主体用 Spring Boot 保证稳定性
- AI 智能体服务层独立部署为 Python (FastAPI) 微服务，通过 REST 接口被 Spring Boot 调用
  - 这样 Python 只管 LLM 调用和 RAG，Java 管业务逻辑和数据安全
  - 两个服务通过 HTTP 内网通信，互不影响

---

### 3.3 数据库与缓存

**需求背景：** 关系型数据库 MySQL 8.0+ / PostgreSQL 14+，Redis 7.0+。

| 层级 | 对比 | 结论 |
|------|------|------|
| 关系型数据库 | MySQL 8.0 vs PostgreSQL 14 | **MySQL 8.0** — 国内高校 DBA 经验更丰富；Spring Boot + MyBatis-Plus 生态最成熟；主从复制运维简单；对于业务系统读写，MySQL 8.0 完全够用 |
| 分析型数据库 | 即上文 Doris | — |
| 缓存 | Redis 7.0 | 无争议；用于会话、热点数据、API 响应缓存；Cluster 模式可选 |
| 会话存储 | Spring Session + Redis | 支持 2小时超时，分布式会话，单点登录兼容 |

**✅ 推荐选型：MySQL 8.0 + Redis 7.0 + Apache Doris（分析层）**

---

### 3.4 消息推送（预警通知渠道）

**需求背景：** 预警推送支持系统内消息 + 邮件，实时性要求有限（分钟级即可）。

| 候选方案 | 说明 |
|---------|------|
| **Spring Boot + JavaMail** | 邮件通知，直接集成，无需额外中间件 |
| **WebSocket（Spring WebSocket）** | 系统内实时消息推送，前端 Element Plus 通知组件接收 |
| **RabbitMQ（消息队列解耦）** | 如预警量大时解耦发送，但高校场景每日预警量有限，可暂不引入 |

**✅ 推荐：Spring WebSocket（系统内消息）+ JavaMail（邮件），初期无需引入消息队列**

---

### 3.5 部署方案

**需求背景：** 私有化部署，Docker Compose / Kubernetes，一键部署脚本，支持 500-1000 并发。

| 方案 | 适用规模 | 运维复杂度 |
|------|---------|----------|
| **Docker Compose** | 单机/小集群（500-1000 并发够用） | 低，一键 `docker-compose up` |
| **Kubernetes (K3s)** | 中大规模，需要弹性伸缩 | 中，需要学习成本 |
| **裸机部署** | 传统方式 | 高，不推荐 |

**✅ 推荐：Docker Compose（主）+ K3s 升级路径（备）**

- 当前高校场景 500-1000 并发，Docker Compose 单机完全够用
- 提供标准 `docker-compose.yml` + `.env` 配置，一键部署
- 如学校已有 K8s 环境，提供 Helm Chart 备选方案
- 服务拆分：前端 Nginx + Spring Boot API + Python AI Service + MySQL + Redis + Doris

---

### 3.6 统一身份认证（SSO）

**需求背景：** 对接学校统一身份认证，实现单点登录，RBAC 权限隔离。

| 候选方案 | 说明 |
|---------|------|
| **CAS 协议对接** | 国内高校统一认证事实标准（90%以上高校使用 CAS Server）；Spring Security CAS 支持完善；直接对接学校现有 CAS Server，无需额外部署 |
| **OAuth2/OIDC + Keycloak** | 现代化协议；但需要学校接入并维护 Keycloak，成本高；且与现有 CAS Server 有迁移问题 |
| **自研 JWT** | 简单但无法对接学校统一认证，不满足需求 |

**✅ 推荐：CAS 协议 + Spring Security CAS Client**

- 直接对接学校现有 CAS Server
- Spring Security 的 `cas-client-core` 成熟稳定
- CAS ticket 验证成功后转换为系统内 JWT（`jjwt` 库），便于前端携带

---

### 3.7 PDF 导出

**需求背景：** 学期体检报告 PDF 导出，院情摘要 Word 导出。

| 候选方案 | 说明 |
|---------|------|
| **iText 7（Java）** | 功能强大，支持中文，但商业版收费（社区版 AGPL 协议） |
| **Apache PDFBox** | 开源免费；但低级 API，表格/图表渲染繁琐 |
| **Flying Saucer（XHTML→PDF）** | 将 HTML 转 PDF，前端设计与导出一致 |
| **前端 html2canvas + jsPDF** | 纯前端方案，截图式导出 |
| **Apache POI（Word）** | Java 操作 docx 标准库；免费开源 |

**✅ 推荐：**
- **PDF 导出：Flying Saucer + Thymeleaf 模板** — 用 HTML 模板定义报告样式，服务端渲染后转 PDF，与前端样式高度一致，无需学习 PDF 底层 API
- **Word 导出：Apache POI 5.x** — 纯 Java，免费，生成结构化 docx，满足院情报告导出需求

## 四、智能体搭建与运营服务技术选型

### 4.1 大语言模型

**需求背景：** 须经国家网信办备案，支持 8000+ token 上下文，不得用于境外训练，支持私有化部署或 API 调用。

| 候选方案 | 备案状态 | 上下文窗口 | 价格（API） | 推理能力 | 数据安全 |
|---------|---------|----------|------------|---------|---------|
| **DeepSeek-V3/R1** | ✅ 已备案 | 64K tokens | 极低（V3: ¥2/M input tokens） | 极强（数学/推理领先） | API 模式数据上传至 DeepSeek 服务器 |
| **通义千问 2.5-72B** | ✅ 已备案 | 128K tokens | 低（¥4/M input tokens） | 强 | API 模式同上 |
| **文心一言 4.0** | ✅ 已备案 | 128K tokens | 中（¥12/M input tokens） | 良好 | API 模式同上 |
| **智谱 GLM-4** | ✅ 已备案 | 128K tokens | 低 | 良好 | API 模式同上 |
| **Qwen2.5-7B/14B 本地部署** | ✅ 已备案（开源版） | 128K tokens | 仅算力成本 | 7B 弱、14B 中等 | 学生数据不出校，最安全 |
| **Llama 3.1 本地** | ⚠️ 境外模型未备案 | 128K tokens | 仅算力成本 | 强 | ❌ 不合规 |

**✅ 推荐：主力 DeepSeek-V3 API + 本地化备选 Qwen2.5-14B**

- **主力方案：DeepSeek-V3 API**
  - 成本最优（约为 GPT-4o 的 1/50）；推理能力在教育问答场景够用
  - 学生数据通过 Prompt 注入（不存储到 DeepSeek），敏感信息脱敏处理后进入 Prompt
  - DeepSeek 与 Python AI 服务在内网调用，在 Prompt 层加入隐私保护系统指令
- **备选/离线方案：Qwen2.5-14B 私有化部署（Ollama）**
  - 使用学校 GPU 服务器本地部署，零数据出校
  - 推理性能：14B 参数在教育 FAQ/文本生成场景满足需求
  - 部署工具：Ollama（开箱即用，支持 GPU 加速）

---

### 4.2 智能体编排与管理平台

**需求背景：** RAG 架构，检索召回率 ≥85%，多步工具调用，Prompt 版本管理，调试台，运行效果监控，50路并发。

| 候选方案 | 类型 | 优势 | 劣势 |
|---------|------|------|------|
| **Dify（开源版）** | 低代码平台 | 可视化知识库管理；Workflow 编排；Prompt 版本管理；调试控制台；使用统计监控；支持 RAG 配置；活跃社区 | 定制化开发能力弱；需要 Docker 部署 |
| **LangChain + LangGraph** | 代码框架 | 最灵活；生态最大；支持复杂 Agent 状态机 | 代码量大；版本迭代快（v0.3频繁破坏性更新）；无内置管理界面 |
| **LlamaIndex** | RAG 专用框架 | RAG 效果好；Index 管理完善；文档检索场景最优 | 缺 Agent 编排能力；需配合 LangGraph 使用 |
| **AutoGen（微软）** | 多Agent对话 | 多 Agent 协作能力强 | 更适合多 Agent 协作场景，本项目单智能体为主 |
| **自研** | 完全定制 | 满足所有定制需求 | 开发周期长（≥3个月）；维护成本高 |

**✅ 推荐：Dify（开源版）作为主平台 + LlamaIndex 作为 RAG 引擎增强**

- Dify 直接满足文档 3.1.7 的「智能体管理后台：Prompt 版本管理、调试、效果监控」要求
- Dify 内置知识库管理（基于 RAG），配合 Milvus 向量库可达 ≥85% 召回率
- Dify 支持 Workflow（多步工具调用），满足 3.1.5 学业数据 API 工具调用要求
- Dify 提供 OpenAPI，Python 后端服务通过 API 调用 Dify 编排的 Agent
- Dify 部署：Docker Compose，与主系统同一 Docker 网络，内网通信

---

### 4.3 向量数据库

**需求背景：** RAG 知识库存储，检索召回率 ≥85%，200条 FAQ + 院校知识库，支持混合检索。

| 候选方案 | 性能 | 运维复杂度 | 与 Dify 集成 | 适用规模 |
|---------|------|----------|------------|---------|
| **Milvus（Standalone）** | ⭐⭐⭐⭐⭐ | 中（Docker 一键） | ✅ 原生支持 | 中大规模 |
| **Qdrant** | ⭐⭐⭐⭐ | 低（单二进制） | ✅ Dify 支持 | 中等规模 |
| **ChromaDB** | ⭐⭐⭐ | 极低（嵌入式） | ✅ Dify 支持 | 小规模（嵌入测试用） |
| **PgVector（PostgreSQL 插件）** | ⭐⭐⭐ | 低（MySQL 已有） | ✅ LlamaIndex 支持 | 小中规模 |
| **Weaviate** | ⭐⭐⭐⭐ | 中 | ✅ Dify 支持 | 中大规模 |
| **Faiss** | ⭐⭐⭐⭐⭐ | 中（纯库，需封装） | ❌ 无服务化 | 科研级 |

**✅ 推荐：Milvus 2.x（Standalone 模式）**

- Dify 原生集成，配置即用
- 支持稠密向量（语义检索）+ 稀疏向量（关键词检索）混合检索，召回率 ≥90% 可达
- Standalone 模式单 Docker 容器，4GB 内存即可运行
- 高校知识库规模（万级文档）完全在 Milvus 舒适区内
- 如资源极其受限，降级方案：**PgVector**（复用已有 PostgreSQL）

### 4.4 Embedding 模型

**需求背景：** 将知识库文档向量化，支持中文教育场景。

| 候选方案 | 类型 | 中文效果 | 成本 |
|---------|------|---------|------|
| **text-embedding-3-small（OpenAI）** | API | 好 | ¥0.08/M tokens，但境外 API |
| **text-embedding-v3（通义千问）** | API | 好 | 免费额度，已备案 |
| **BGE-M3（BAAI，本地）** | 本地 | 极佳（中文专项优化） | 仅算力（CPU 可运行） |
| **BCE-Embedding（网易有道）** | 本地 | 极佳（RAG 专项优化） | 仅算力 |

**✅ 推荐：BGE-M3 本地部署**

- BAAI（北京智源研究院）出品，中文 RAG 场景 Benchmark 第一
- 支持稠密+稀疏向量同时输出，与 Milvus 混合检索完美配合
- 模型大小约 500MB，CPU 推理即可满足知识库构建需求
- 与 Dify 集成：通过 Ollama 提供 Embedding API 端点

### 6.2 关键风险与应对

| 风险 | 描述 | 应对方案 |
|------|------|---------|
| **数据源对接阻力** | 教务/学工系统不开放接口，需学校协调 | 合同中明确学校须提供接口文档及联调环境；备选文件导入方案 |
| **DeepSeek API 稳定性** | API 调用受网络/限速影响 | 实现请求重试机制；在学校部署 Qwen2.5-14B 作为离线降级 |
| **Dify 版本迭代** | Dify 迭代较快，接口可能变化 | 锁定版本（0.10.x），升级前在测试环境验证 |
| **Doris 运维能力** | 团队可能对 Doris 不熟悉 | 选 Doris Standalone 单 FE+BE 模式，降低运维复杂度；官方文档中文完善 |
| **等保三级** | 测评周期长，可能影响验收 | 开发阶段同步推进代码安全审查；与学校网络安全团队提前对接 |
| **LLM 数据合规** | 学生数据通过 API 传输 | Prompt 层强制脱敏（学号→匿名ID，姓名→哈希）；敏感字段仅在学校内网范围使用 |

### 6.3 三大项目接口依赖关系

```
大项一（数据工程）
    └─ 输出：Doris ADS 层应用宽表 + 预警事件表
              ↓
大项二（系统平台）
    └─ Spring Boot API 读取 Doris ADS 层数据
       └─ AI 画像解读调用大项三 AI 服务接口
              ↓
大项三（智能体服务）
    └─ Dify Agent 工具调用 → Spring Boot API → Doris ADS 层
```

三大项存在强依赖：大项一必须先于大项二/三完成核心数据接入；建议开发顺序：
1. **第1个月：** 数据源对接 + ODS 层建设（大项一前置）
2. **第2-3个月：** DWD/DWS/ADS 建设 + 系统前后端开发并行
3. **第4个月：** 智能体平台搭建 + 知识库建设
4. **第5个月：** 联调测试 + 等保整改 + UAT
