# 数据接入说明

## 1. 可行性结论

本项目后端已经直接连接本地 MySQL 数据库 `academic_nav`，所有业务接口都是实时读库：

- 你往数据库里插入、修改、删除数据，现有接口下一次请求就会读到新数据，不需要改后端代码。
- 后端目前的数据来自 Flyway 迁移脚本 `V3__init_business_data.sql`，你可以把它当成建表和种子数据模板。
- 校方将来如果提供 REST API 或只读数据库账号，系统已有 `AcademicDataSource` 适配层预留位：实现一个 `SchoolApiDataSource` 做字段映射和同步即可，业务层代码不用改。

所以结论是：

1. 本地自建数据集：现在就可以做，直接写进 `academic_nav` 的对应表。
2. 校方数据库 API 接入：可行，但需要对方提供接口文档，我们做适配器转换字段。

## 2. 本地数据集需要哪些表

以下是当前后端真正在用的核心表，做数据集时按这些表填即可。

### 基础档案

| 表 | 必填字段 | 说明 |
|---|---|---|
| `t_department` | `name` | 学院 |
| `t_major` | `name`, `department_id` | 专业，挂在学院下 |
| `t_class` | `name`, `grade`, `major_id`, `advisor_id`, `total_students` | 班级，`advisor_id` 指向 `t_teacher.id` |
| `t_user` | `account`, `name`, `password`, `role`, `college`, `major`, `class_name`, `grade` | 登录账号，`role` 用 `student/teacher/course_teacher/department/dean` |
| `t_student` | `student_id`, `user_id`, `class_id`, `major_id`, `department_id`, `gpa`, `alert_level` | 学生档案，`rank/total_credits/required_credits` 可选 |
| `t_teacher` | `teacher_id`, `user_id`, `department_id`, `is_class_advisor`, `class_id` | 教师档案，班主任 `is_class_advisor=1` |

### 教学数据

| 表 | 必填字段 | 说明 |
|---|---|---|
| `t_course` | `code`, `name`, `credits`, `type` | 课程 |
| `t_course_class` | `course_id`, `term`, `class_name`, `teacher_id`, `max_students`, `enrolled_students` | 开课班级，`term` 格式如 `2024-2025-1` |
| `t_grade` | `student_id`, `course_class_id`, `score`, `grade_point`, `status`, `term` | 学生成绩，`status` 用 `pending/passed/failed/retake` |

### 学业画像

| 表 | 必填字段 | 说明 |
|---|---|---|
| `t_gpa_history` | `student_id`, `term`, `gpa`, `avg_gpa` | 每学期 GPA 历史 |
| `t_profile_score` | `student_id`, `term`, `dimension_key`, `label`, `score` | 五维画像，`dimension_key` 用 `academic/practice/quality/culture/health` |
| `t_health_report` | `student_id`, `term`, `total_score` | 体测报告，`items` 是 JSON 数组 |

### 预警（可选）

| 表 | 必填字段 | 说明 |
|---|---|---|
| `t_alert` | `student_id`, `level`, `type`, `title`, `status` | 预警记录，`level` 用 `yellow/orange/red` |
| `t_intervention_record` | `alert_id`, `teacher_id`, `intervention_date` | 教师干预回填，由系统写入 |

## 3. 最小可用数据集建议

想让现有接口全部跑通，至少准备：

- 1 个学院、1 到 2 个专业、1 个班级；
- 1 个班主任账号 + 1 个任课教师账号；
- 10 到 12 个学生账号；
- 每个学生 5 个学期的 `t_gpa_history`；
- 每个学生每学期 5 条 `t_profile_score`；
- 若干 `t_course` / `t_course_class` / `t_grade`，用于课程统计和挂科名单；
- 每学生 1 条 `t_health_report`；
- 预警数据可选，但建议放几条，用于验证预警模块和权限隔离。

密码统一用 BCrypt 加密后的 `123456`，直接复制 `V3` 里的哈希值即可。

## 4. 校方 API 接入需要确认的信息

将来拿到校方接口后，需要对方提供：

1. API 文档、Base URL、测试/生产环境地址；
2. 鉴权方式：Token、AppKey、OAuth2 或其他；
3. 每个实体的接口：学生、班级、专业、课程、选课、成绩、GPA、考勤、体测、就业等；
4. 每个接口的返回字段样例、字段类型、枚举值；
5. 数据更新频率，是全量还是增量，有没有时间戳字段；
6. 分页方式、筛选参数、错误码、限流规则；
7. 数据敏感性和脱敏要求。

拿到这些后，我们实现 `SchoolApiDataSource` 做三件事：

- 调用校方接口；
- 把校方字段映射成现有表结构；
- 按频率同步到 `academic_nav`，或者查询时实时穿透。

## 5. 推荐推进顺序

1. 按第 2、3 节准备一份自己的数据集（SQL 或 Excel）；
2. 导入 `academic_nav`，登录现有账号验证各端接口；
3. 拿到校方 API 文档后，先写一份“校方字段 -> 本地字段”映射表；
4. 实现数据源适配器并做增量同步，验收标准是前端页面字段不变、数据真实。
