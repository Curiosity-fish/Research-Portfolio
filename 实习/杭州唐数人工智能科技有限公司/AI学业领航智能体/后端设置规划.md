## 一、现状盘点与差距

### 1.1 后端现状（以代码为准）

| 项目 | 现状 |
|------|------|
| 框架 | Spring Boot 3.2.5，Java 21，MyBatis-Plus 3.5.7 |
| 认证 | Spring Security + JWT（jjwt 0.12.6），登录/登出已实现 |
| 数据库 | MySQL + Flyway，已有 `V1__init_user.sql`、`V2__add_course_teacher.sql` |
| 缓存 | 已引入 Redis starter，JWT 黑名单已用 Redis 实现（`TokenBlacklistService`） |
| API 文档 | SpringDoc，Swagger UI 地址 `/swagger-ui.html` |
| 数据源抽象 | 已有 `AcademicDataSource` 接口 + `MockAcademicDataSource`，但只有 GPA/排名/学分 3 个方法 |
| 业务接口 | 只有 `POST /api/auth/login`、`POST /api/auth/logout`，无任何业务 API |
| 统一返回 | `Result<T>`（code/message/data），无 `timestamp` |
| 异常处理 | `GlobalExceptionHandler` 返回 `Result`，但业务异常 HTTP 状态码仍是 200 |
| 监控 | pom 未引入 actuator，`SecurityConfig` 中 `/actuator/health` 实际不可用 |

### 1.2 前端现状（决定 API 的“客户”）

- Vue 3 + Vite + TypeScript + Pinia + Element Plus + ECharts。
- `src/utils/request.ts`：axios 封装，`baseURL: '/api'`，自动带 `Authorization: Bearer <token>`，响应拦截器直接 `return res.data`。
- `src/stores/auth.ts`：登录调用 `POST /auth/login`，期望 `data` 里返回 `{ token, user }`；登出调用 `POST /auth/logout`。
- 五个端：`/student`、`/teacher`、`/course-teacher`、`/department`、`/dean`，目前页面数据几乎全部来自 `src/mock/*`。
- AI 对话 `AgentChat.vue` 已预留 Dify / E-Agent 两种外部流式 API 的调用代码，后端接入后可切换为 SSE。
- 页面数据字段以 `src/types/index.ts` 与 `src/mock/*.ts` 为准，后端返回 JSON 字段名必须与前端一致（camelCase）。

### 1.3 主要差距

| 差距 | 影响 | 处置 |
|------|------|------|
| 业务 API 全部缺失 | 前端只能 mock，无法上线 | 按本规划逐模块实现 |
| 登录失败时 HTTP 200 + code 400 | 前端拦截器读不到 `err.response`，登录失败提示不生效 | 统一异常返回真实 HTTP 状态码 |
| 无 `GET /api/auth/me` | 刷新页面无法恢复登录态 | 补接口，前端路由守卫调用 |
| 无角色级 URL 鉴权 | 任何登录用户可访问所有业务 API | SecurityConfig 增加角色规则 |
| `AcademicDataSource` 过于单薄 | 无法承载成绩、考勤、体测、课程等数据 | 扩展接口 + 学校 API 适配器 |
| 无告警、画像、GPA 历史等表 | 无法持久化业务数据 | Flyway 新增 V3+ 迁移 |
| 无 SSE/WebSocket | AI 对话、预警实时推送缺通道 | 增加 SSE 对话 + WebSocket 推送 |
| 前端类型文件有漂移 | `types/index.ts` 缺少 `HealthReport`、`ResourceItem`、`PeerStudent` 等被引用的类型 | 前端与后端同步补类型，按页面增量替换 |

## 二、总体目标与架构

### 2.1 目标

以 `后端架构设计.md` 为蓝图，以现有 `academic-navigation-backend` 为基座，实现五个端（学生、班主任、任课教师、系主任、院长）完整业务 API，并把教务、考勤、体测、就业、院校库等外部数据统一收敛到数据源适配层，保证“前端字段不变、数据源可切换”。

### 2.2 分层架构

```text
前端五端 (Vue3 + TS)
        |
        | HTTP/HTTPS REST + SSE + WebSocket
        v
API 层：Controller（参数校验、权限注解、统一 Result）
        |
Service 层：业务编排、预警规则、AI 会话、统计计算
        |
Mapper 层：MyBatis-Plus（本系统业务表）
        |
        +-- AcademicDataSource 适配层（学校教务/学工/体测/就业等外部系统）
        |     |-- MockAcademicDataSource（开发/演示）
        |     `-- SchoolApiDataSource（生产，按配置切换）
        |
基础设施：MySQL 8 / Redis 7 / RabbitMQ / XXL-Job / Actuator+Prometheus
```

### 2.3 技术栈核对

| 组件 | 设计文档要求 | 现状 | 规划动作 |
|------|------|------|---------|
| Spring Boot 3.x | ✅ | 3.2.5 | 保持 |
| MySQL 8.0 | ✅ | 驱动已引入 | 保持 |
| Redis 7.x | ✅ | starter 已引入 | 补缓存策略与键设计 |
| MyBatis-Plus | ✅ | 3.5.7 | 保持，补数据权限拦截器 |
| Spring Security + JWT | ✅ | 已实现 | 补角色鉴权与 `/auth/me` |
| Knife4j/SpringDoc | ✅ | SpringDoc | 保持，补接口注解 |
| RabbitMQ | 设计文档要求 | 未引入 | P2 预警通知与异步任务时引入 |
| XXL-Job | 设计文档要求 | 未引入 | P2 数据同步/报表生成时引入 |
| Actuator + Prometheus | 设计文档要求 | 未引入 | P0 补 actuator 依赖与指标暴露 |

## 三、工程结构与模块划分

建议在 `com.zjnu.academic` 下按业务域分包：

```text
com.zjnu.academic
├── AcademicNavigationApplication.java
├── auth                 # 登录、登出、/auth/me、CAS 回调
│   ├── controller
│   ├── dto
│   └── service
├── user                 # 用户（保留现有）
├── student              # 学生端：Dashboard、画像、GPA 趋势
├── teacher              # 班主任端：驾驶舱、GPA 进退、课程统计
├── course-teacher       # 任课教师端：我的课程、学情预警
├── department           # 系主任端：专业态势、课程热度、培养方案
├── dean                 # 院长端：全院仪表盘、预警总览
├── alert                # 预警：规则、列表、确认、干预、推送
├── development          # 发展引导：路径、职位、院校
├── health               # 体测报告
├── agent                # AI 智能体：配置、会话、SSE、外部模型适配
├── common
│   ├── result           # Result / PageResult
│   ├── exception
│   └── util
├── config               # Security、Redis、WebSocket、RateLimit、MyBatis-Plus
├── datasource           # AcademicDataSource + mock + school adapter
└── job                  # XXL-Job 定时任务（同步、预警、报表）
```

分层约定：
- Controller 只做参数校验与权限声明，不写业务。
- Service 承担业务规则与统计计算。
- Mapper 只做本系统库的持久化。
- 外部数据一律通过 `AcademicDataSource` 获取，业务代码不直接依赖学校 API。

## 四、数据库设计

### 4.1 设计原则

1. 保留现有 `t_user`，其余业务表以 `t_` 前缀新增，Flyway 管理版本。
2. 字段名与前端 `types/index.ts` 的 camelCase 一一对应，DB 使用 snake_case，靠 MyBatis-Plus 自动映射。
3. 预警中的 `failed_courses` 用 JSON 数组存储，返回时必须是数组，不能为 null。
4. 所有表带 `created_at` / `updated_at`，统计类数据落库前先算好，避免每次请求实时扫大表。

### 4.2 核心表清单

| 表 | 用途 | 关键字段 |
|----|------|---------|
| `t_user`（已有） | 登录账号、角色、学院专业班级 | account, name, password, role, college, major, class_name, grade |
| `t_student` | 学生档案 | student_id, user_id, class_id, major_id, department_id, gpa, rank, total_students, alert_level, total_credits, required_credits |
| `t_teacher` | 教师档案 | teacher_id, user_id, department_id, title, is_class_advisor, class_id |
| `t_department` | 学院 | name, code, dean_id |
| `t_major` | 专业 | name, code, department_id, degree_type |
| `t_class` | 班级 | name, grade, major_id, advisor_id, total_students |
| `t_course` | 课程 | code, name, credits, type(required/elective/public), department_id |
| `t_course_class` | 课程班级（开课） | course_id, term, class_name, teacher_id, max_students, enrolled_students, status |
| `t_grade` | 成绩 | student_id, course_class_id, score, grade_point, status(pending/passed/failed/retake), term, exam_date |
| `t_alert` | 预警记录 | student_id, level(yellow/orange/red), type, reason, gpa, absences, failed_courses(JSON), trigger_date, status, handler_id, handle_note, student_confirmed_at, pushed_at |
| `t_intervention_record` | 教师干预回填 | alert_id, teacher_id, intervention_date, methods(JSON), content, student_response, follow_up_plan |

| `t_school_cache` | 院校库缓存 | type(grad/overseas), name, tier, programs(JSON), admission_gpa, language_requirement, highlights(JSON), match_score, official_url, deadline |
| `t_ai_agent` | 智能体配置 | code, name, description, icon, svg_icon, img_url, icon_bg, category, group_name, roles(JSON), status, usage_count, preset_questions(JSON), accent_color, welcome_message, data_used(JSON), external_api(JSON), iframe_url |
| `t_ai_conversation` | AI 会话 | user_id, agent_id, title, status |
| `t_ai_message` | AI 消息 | conversation_id, role, content, tokens |
| `t_operation_log` | 操作审计（可选） | user_id, module, action, params(JSON), ip, created_at |

### 4.3 与前端类型的映射（关键）

| 前端类型 | 后端来源 | 注意 |
|---------|---------|------|
| `User` | `t_user` | 登录返回 `user` 必须含 id/account/name/role/college/major/className/grade |
| `Student` | `t_student` + `t_user` | `grade` 前端显示为“2022级”，DB 存年份即可 |
| `StudentDashboardData` | `t_student` + `t_gpa_history` + `t_alert` 聚合 | `alertCount` 取当前学期 pending+processing 数 |
| `AcademicProfile` | `t_profile_score` + `t_gpa_history` | `details` 是 JSON 数组 |
| `AlertItem` | `t_alert` | `failedCourses` 必须返回数组，`pushedAt` 用字符串 |
| `TeacherDashboardData` | 班级维度聚合 | `gradeDistribution` 固定四段：优秀/良好/中等/预警 |
| `DevelopmentPath` | 规则引擎 + 画像聚合 | `key` 固定：graduate/overseas/civil/employment/institution |
| `DepartmentData` | 专业维度聚合 | `gradeGpaTrend` 按年级分组 |
| `DeanData` | 学院维度聚合 | `departmentRanking` 含 healthScore/passRate/avgGpa |
| `AgentConfig` | `t_ai_agent` | 字段与 `mock/agents.ts` 的 `AgentConfig` 完全一致 |

### 4.4 种子数据（Flyway V3）

`V3__init_business_data.sql` 建议包含：
- 1 个学院、2-3 个专业、2-4 个班级；
- 12 名左右学生（覆盖 none/yellow/orange/red）；
- 6-8 门课程、若干课程班级与成绩记录；
- 5-10 条预警记录（含 `failed_courses` JSON）；
- 5 个维度的画像分数与 5 个学期 GPA 历史；
- 与 `mock/agents.ts` 对齐的智能体配置初始化数据；
- 1-2 条干预记录。

## 五、API 接口规范与数据格式

### 5.1 统一响应格式

保持现有 `Result<T>`，补充 `timestamp`：

```json
{
  "code": 200,
  "message": "success",
  "data": {},
  "timestamp": 1750000000000
}
```

错误码与 HTTP 状态码对应：

| code | HTTP | 含义 |
|------|------|------|
| 200 | 200 | 成功 |
| 400 | 400 | 参数错误 |
| 401 | 401 | 未认证/Token 失效 |
| 403 | 403 | 无权限 |
| 404 | 404 | 资源不存在 |
| 500 | 500 | 服务内部错误 |

**必须整改：** `GlobalExceptionHandler` 对 `BusinessException` 返回与 code 一致的 HTTP 状态；前端 `request.ts` 在响应拦截器中增加 `if (res.data.code !== 200) return Promise.reject(...)`，并读取 `res.data.message` 提示。

### 5.2 分页格式

```json
{
  "list": [],
  "total": 120,
  "page": 1,
  "size": 20
}
```

后端统一 `PageResult<T>`，分页参数 `page`（从 1 开始）、`size`（默认 20，最大 100）。

### 5.3 公共查询参数

- `term`：学期，统一格式 `2024-2025-1`。前端展示层可自行转成“2024-2025 第一学期”，API 契约固定一种。
- `level`：`yellow|orange|red`
- `status`：`pending|processing|resolved`
- 列表接口均支持 `keyword`（学生姓名/学号模糊搜索）。

### 5.4 认证模块

| 接口 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 登录 | POST | `/api/auth/login` | 现有接口，保留 |
| 当前用户 | GET | `/api/auth/me` | 新增，刷新页面恢复登录态 |
| 登出 | POST | `/api/auth/logout` | 现有接口，保留 |
| CAS 回调（后续） | POST | `/api/auth/cas-callback` | 接收 ticket，校验后返回 JWT |

### 6.5 同步与容错

1. 接口幂等：以 `(studentId, courseClassId, term)` 唯一键 upsert。
2. 失败重试：RabbitMQ 延迟队列或 XXL-Job 补跑，单条失败不影响批次。
3. 降级：外部系统不可用时返回上次同步的库内数据，并在响应头或日志标记 `source: cache`。
4. 凭证管理：`appKey/secret` 放环境变量，不进代码仓库。
5. Mock 切换：`application.yml` 配置 `academic.datasource.provider: mock|school`。

```yaml
academic:
  datasource:
    provider: mock
  school:
    base-url: ${SCHOOL_API_BASE_URL:}
    app-key: ${SCHOOL_API_APP_KEY:}
    app-secret: ${SCHOOL_API_APP_SECRET:}
    connect-timeout: 3000
    read-timeout: 15000
```

## 七、安全与权限

### 7.1 SecurityConfig 角色规则

```text
/api/auth/**, /swagger-ui/**, /api-docs/**, /actuator/health   permitAll
/api/student/**                                                  hasRole STUDENT
/api/teacher/**                                                  hasAnyRole TEACHER, COURSE_TEACHER
/api/course-teacher/**                                           hasRole COURSE_TEACHER
/api/department/**                                               hasRole DEPARTMENT
/api/dean/**                                                     hasRole DEAN
/api/agents/**, /api/alerts/**, /api/development/**              authenticated（内部再做数据范围校验）
```

### 7.2 数据范围矩阵

| 角色 | 可见范围 |
|------|---------|
| student | 仅本人数据 |
| teacher | 所负责班级的全部学生 |
| course_teacher | 所授课程班级的学生成绩 |
| department | 所属专业/系的数据 |
| dean | 全院数据 |

实现方式：Service 层统一从 `SecurityContext` 拿 `userId/role`，生成 `DataScope` 条件；必要时用 MyBatis-Plus 拦截器追加 SQL 条件，避免漏改某接口。

### 7.3 其它安全项

- JWT 有效期 24h，黑名单用 Redis（已实现），补 `/api/auth/me` 供前端恢复会话。
- 密码 BCrypt strength 12（已实现），登录失败不区分账号/密码错误。
- 参数校验用 `@Validated` + DTO 注解，避免手写 if。
- 接口限流：Redis + Lua（按用户/IP + 接口维度），AI 对话单独限流。
- CORS 白名单保留开发端口，生产由 Nginx 同源代理。
