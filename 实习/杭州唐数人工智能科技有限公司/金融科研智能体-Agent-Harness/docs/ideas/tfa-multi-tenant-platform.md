# TFA 多租户科研 Agent 平台

> 状态：需求已确认（interview-me → advise-project-approach → idea-refine），方向 A 已定。
> 日期：2026-08-20

## Problem Statement

**How Might We** 让校内师生在**自托管、多租户**的平台上，把 AI 技能和科研数据集组织成**私有 / 课程课题组 / 公开**三层库，并由**项目**决定每个 agent 会话能访问哪些库，在**沙箱**中聊天式跑科研——**1 个月内交付一个可演示的核心闭环**。

## Recommended Direction

**方向 A：项目作用域的库 + 沙箱会话（已确认）**

- 控制面（Web + 数据库 + 资源 ACL）与执行面（Docker 每会话）分离
- 技能库 = git 仓库 + 三层目录（用户私有 / 课程共享 / 公开），安装 = `git clone` 到对应库目录，复用 TFA 现成 skills 加载机制（`docs/skills.md`：`~/.tfa/agent/skills/`、settings `skills` 数组、`/skill:name` 命令）
- 数据集 = 上传 + 按项目权限**只读挂载**进会话容器
- 模型 = 服务器自部署（Ollama，GPU）或用户自带 Key，二选一
- 管理端只做最小可用：用户 / 课程组 / 禁用与下架

## Key Assumptions to Validate

- [ ] **TFA 能按项目注入 `settings.skills` 路径实现作用域隔离** —— 技术核心假设，开工第一周验证（最小测试：两个项目各注入不同技能目录，确认互不可见）
- [ ] 数据集**只读挂载**进容器可行且不炸存储（vs 复制）
- [ ] GPU 服务器同时跑 Ollama + 多个 agent 容器，内存够用（≤100 用户、低并发）
- [ ] 老师愿意自己建课程组并维护成员（管理端要轻）
- [ ] "先上线后审核"可接受（管理员手动下架兜底）

## MVP Scope（1 个月）

1. 登录：管理员建号
2. 项目：私有 / 课程课题组分类
3. 库：GitHub 安装 skill（clone 入库）、平台内自研/上传、数据集上传；三层可见性在存储层落地
4. 会话：选项目 → 起 Docker 容器（TFA）→ 注入该项目的库路径 + 数据集只读挂载 → 聊天式跑科研
5. 管理端最小可用：用户管理、课程组管理、禁用账号、公开资源下架

## Not Doing (and Why)

- **技能市场/搜索/评分** —— SkillHub 等开源方案已存在，以后部署即可，不自己造
- **token 计费 / 中央密钥库** —— BYOK + 自部署模型，无此需求
- **微 VM 隔离** —— 规模未到；保持控制面/执行面分离，未来平滑升级
- **学校 SSO / 移动端** —— 范围外
- **自动化审核流 / 监控仪表盘 / 用量统计** —— 管理端先做最小可用，二期再说
- **V2 的反向（薄 Web 壳）** —— 客户演示需要界面，被否

## Open Questions

- 课程组与项目的关系：一个课程组 = 一个共享项目，还是课程组下有多个项目？（影响 ACL 表结构）
- Ollama 接入 TFA 的具体配置方式（OpenAI 兼容端点？`packages/ai` 已有 llama-cpp 支持，需确认 route）
- 数据集上传的大小上限与格式限制（首批要不要限制）

## 背景上下文（供后续引用）

- 产品：把现有 TFA harness（tech-finance-agent，pi 框架改造版）改造成多用户 Web 平台
- 用户：老师 + 学生，首批 ≤100 人，校内可信用户，单台中等配置服务器（带 GPU）
- 账号：管理员建号为主
- 使用方式：聊天式 —— 开 agent 会话 → 选项目 → 加载 skill → 挂数据集 → 对话式跑科研
- 权限链路：用户 → 项目（作用域）→ 库（三层可见性）→ 会话/成果
- 隔离方案：控制面/执行面分离 + Docker 每会话（TFA 纯 Docker 模式），cgroup 限额、磁盘配额、会话超时；未来可升级微 VM
- 竞品参照：Open WebUI（组级资源 ACL 模型）、Dify（多租户+知识库+sandbox）、JupyterHub（教育多用户容器）、SkillHub（技能市场已开源）
