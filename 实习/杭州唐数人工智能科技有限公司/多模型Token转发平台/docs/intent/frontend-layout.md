# 前端布局意图文档

> 本文档由 interview-me 流程产出，用户已于 2026-09-03 逐行确认（explicit yes）。后续所有前端设计与实现决策以本文档为基准；如需变更，先更新本文档再实施。

## 意图重述

- **Outcome**：`school-api-v1/web/` 下新建 Vue 3 + TypeScript + Vite + Element Plus 管理端，全局布局统一为一套自适应骨架——内容区宽度方向真实吃满任何屏幕（密度填充：字号恒定，靠统计卡加列、表格列拉伸、栅格自适应消化宽度，消灭大片空白）；高度方向整页和表格区零滚动条，每页行数随视口高度动态计算，溢出全部交给分页；弹窗允许内部滚动。
- **User**：用户本人作为管理员日常操作；大屏（电视/投影）观众只看 Dashboard 类展示数据，不在大屏前操作。
- **Why now**：后端 Phase 1–7 已交付、API 契约稳定，进入前端窗口；旧前端（`school-api/frontend/`）24 个页面的信息架构和交互流程可直接参考，但其固定宽度容器造成的响应式断档空白必须在新版根治。
- **Success**：在 1366×768 和 1920×1080（以及更大屏/电视）下逐页验收：无整页滚动条、表格区无滚动条且行数随高度自适应、无大片空白区；Dashboard 投到电视远观可读；旧前端的布局问题不复现。
- **Constraint**：最小适配底线 1366×768 笔记本，完整功能可操作；字号/控件尺寸不随屏幕放大（密度填充策略，Dashboard 大屏增强除外）；API 层、认证、金额处理按 `learning/frontend-handoff.md` 契约全新实现（micro-currency 换算、JWT 401 跳登录、token 明文一次性展示）。
- **Out of scope（一期明确不做）**：用户端 `/user` 页面（随后二期）；Dashboard 外的统计图表深化；手机端（<1366px 不保证体验）；旧前端有但新后端无对应 API 的页面（功能开关、使用说明等）。

## 已确认的决策点

| 决策点 | 结论 |
|--------|------|
| 技术栈 | Vue 3 + TypeScript + Vite + Element Plus（方案 A：保留 Vue 技术栈连续性，引入组件库解决表格/表单密度问题） |
| 应用拆分 | 一个工程内 `/admin` + `/user` 两套布局与路由守卫（一期先实现 `/admin`） |
| 第一期范围 | 管理端优先：登录、用户/Token、平台/账号/模型、订单/流水、通知 |
| 工程位置 | `school-api-v1/web/`（位于后端仓库内部，非平级） |
| 最小适配屏幕 | 1366×768 笔记本，完整功能可操作 |
| 滚动策略 | B 档为主：整页无滚动条、表格区不出内部滚动条、行数随视口高度动态计算、溢出走分页；弹窗放宽到 A（弹窗内部允许滚动） |
| 核心痛点 | 旧前端响应式断档：固定宽度容器在大屏上两侧大片留白，小屏装不下；新版必须让内容区随屏幕真实伸缩 |
| 大屏场景 | 电视/投影以"看"为主（Dashboard 数据上墙），操作在桌面显示器完成 |
| 宽度策略 | 密度填充：字号/控件尺寸恒定，大屏靠加列、拉伸、栅格消化宽度；Dashboard 单独做大屏增强（远观可读） |
| 视觉风格 | 延续旧前端设计令牌（品牌色、CSS 变量、亮暗主题），不做全新视觉设计 |

## 关键依据

- 旧前端 `school-api/frontend/` 约 10700 行，14 个管理端页面 + 10 个用户端页面，信息架构和交互流程已验证，可作页面级参考；但 API 层、认证方式、金额单位与新后端契约不同，必须重写。
- 旧前端无 UI 组件库，纯手写 Tailwind，已出现 `UsersView.vue` 1671 行这类巨型单文件，表格/表单样板代码成本被实践证实过高。
- 技术栈选型放弃 React + AntD 的理由：旧代码参考价值限于信息架构层，Vue 换 React 的收益不足以抵消重写成本；放弃纯 Tailwind 复用旧代码的理由：继承旧代码质量问题，与"不滚动 + 翻页 + 密度填充"的骨架统一目标冲突。
